Agent 工作流的难点往往出现在模型调用之外：一次执行属于哪个任务，输出能否进入下一步，失败如何恢复，谁有权批准最终成果。

BSC 的历史角色分工与后续成果治理、HotScript 的 Task / Worker / Checkpoint / Approval，提供了讨论这些问题的具体材料。它们的存在不等同于当前整链已经完成验证。

## 把职责与执行路径分开

SOP、Risk、Strategy 是分析职责；串行、并行、重试或人工接管是执行策略。图里画了三个 Agent，不能替代真实的执行记录。描述架构时，需要分别说明逻辑职责与当前实际运行路径。

同样，“调用完成”与“任务完成”也不是同一个状态。后者可能还依赖输出检查、人工批准与归档回读。

## 用契约明确交接

下面是说明性的接口草图，目的是展示哪些信息值得保留，不代表某项目已经采用这一确切结构。

```typescript
type Handoff = {
  taskId: string;
  artifactVersion: string;
  sourceRefs: string[];
  decision: "review" | "approved" | "rejected";
  approvedBy: string | null;
};
```

关键问题是批准对象是否稳定、来源能否回读、未批准的结果能否被错误地当作正式成果使用。字段名字可以变化，这些约束需要进入实现与测试。

## 恢复需要可识别的基线

Checkpoint 的意义不仅是保留进度，还需要让下一次执行知道可以从哪里继续，以及哪些外部动作不能重复。对于涉及文件、事件或业务状态的任务，重复执行可能造成不同后果。

这是一项设计要求。当前材料不足以将所有故障恢复场景都标记为已通过；BSC 的真实归档回读与恢复仍是验收缺口。

## 验证机制与价值分别进行

合成项目适合检查工具契约、权限控制和状态变化。真实任务价值需要真实问题、合理样本与操作者判断。BSC 的 2026-10-30 Dify 实验使用合成项目，应保留这个标签。

设计一个可信的 Agent 工作流，意味着既能解释它如何前进，也能解释它何时必须停止，以及哪些结果仍然没有证据。
